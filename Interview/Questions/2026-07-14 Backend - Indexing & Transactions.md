| 4   | Concurrency              | Design the transaction for transferring money from account A to account B. What could go wrong with naive debit-then-credit, and how do locking order + `SELECT ... FOR UPDATE` prevent a deadlock when two transfers happen in opposite directions at once? | --Flow design--<br>- To avoid deadlock: <br>Need to design flow with correct order implement in transaction<br>- Example: use select ... for update to lock the rows first, ensure that row cannot be used by any other.<br>- Flow: <br>+ In tran1: select for update acc1 & acc2<br>+ In tran2: select for update acc1 & acc2 (Locked)<br>+ Back to tran1: The logic happen normally and commit<br>+ Back to tran2: after tran1 commit, select will be done and the logic transfer nomally now --> Deadlock resolve<br>                                                                                                                                                                                                                    | **3/5** — You correctly showed that when both transactions lock accounts in the *same* order, the second one just blocks and waits (no deadlock) rather than explaining *why* that ordering matters. Two gaps: you didn't address the naive-debit-then-credit failure mode, and you didn't spell out the actual deadlock case (opposite lock order) or the general rule that fixes it. | Naive debit-then-credit (two separate, unwrapped statements) risks partial failure: if the process crashes or the network drops after the debit commits but before the credit runs, money vanishes — there's no atomicity. Wrapping both in one DB transaction fixes that, but introduces a deadlock risk: if Transfer A→B locks account A then B (`SELECT ... FOR UPDATE`), while concurrently Transfer B→A locks B then A, each transaction ends up holding one lock and waiting on the other — a circular wait, which the DB detects and resolves by aborting one of them. The fix is a **consistent global lock order independent of transfer direction** — e.g., always lock the lower account ID first, regardless of which account is "from" or "to." Then every concurrent transfer touching the same two accounts requests locks in the same order, so at most one waits — never a cycle.                                                                                                                                                                                                                                                                                                                                                                                                            |
| 5   | Concurrency              | A client's request times out but the server-side write actually succeeded. On retry, how do idempotency keys prevent a double-charge, and where would you enforce that (app layer vs. DB constraint)?                                                        | From the client side should create an idempotency key before excuting a transaction, when it retry, send that key to retry the transaction. If the transaction has been succesfully, server will reject that                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | **3/5** — Directionally right (key generated client-side, sent on retry, server recognizes it's already done), but light on mechanism and didn't answer "app layer vs DB constraint" at all.                                                                                                                                                                                           | More precisely: the client generates a unique idempotency key per logical operation attempt (e.g. a UUID, stable across retries of the *same* attempt) and sends it with the request. Enforce it with a **UNIQUE constraint** on the key in the DB (a dedicated table, or a column on the resulting row) — that's the real source of truth, because an app-layer "check then insert" is itself a race: two retries can both pass the check before either inserts. Flow: begin transaction → attempt to INSERT a row keyed by the idempotency key alongside the business effect (e.g. the ledger entry) → on a UNIQUE-violation, the operation already happened — look up the stored result and return it instead of re-running side effects → commit. Store the *response*, not just a flag, so a retry gets the exact same result back. Bottom line: DB constraint = correctness guarantee; app layer is just an optional fast-path/early-exit and where you shape the cached response.                                                                                                                                                                                                                                                                                                                      |
| 6   | Concurrency              | Frame this without naming a mechanism first: "Two users can update the same inventory count at the same time." What's the invariant you must not violate, and only then — what isolation level or locking strategy enforces it?                              | The invariant is the atom chracteristic, if we violate this 2 users can udate the same inventory count at the same time<br>The isolation level forcing this is read committed                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | **2/5** — The invariant stated ("the atom characteristic") is too vague to be useful, and the isolation level named is actually wrong: READ COMMITTED does **not** prevent this race. This is worth re-drilling since the isolation-level claim would be a real interview miss.                                                                                                        | Invariant: no two concurrent transactions may both read the same inventory count and independently write a decremented value — that "lost update" overstates what's left (oversells) because one of the two real decrements silently disappears. READ COMMITTED does **not** enforce this: T1 reads count=10, T2 reads count=10 before T1 commits, both compute 10-1=9 and write 9 — two units sold, but the count only dropped by one. This is the textbook lost-update anomaly, and READ COMMITTED explicitly allows it (each statement sees a fresh snapshot, but the read-modify-write isn't atomic). Fixes: (1) explicit row lock — `SELECT count FROM inventory WHERE id=X FOR UPDATE` inside a transaction, forcing the second transaction to block until the first commits; (2) the usually-best fix for a simple counter — a single atomic statement: `UPDATE inventory SET count = count - 1 WHERE id = X AND count >= 1`, letting the DB do the read+write atomically with no app-level race window; (3) SERIALIZABLE isolation, which detects the conflict and aborts one transaction with a serialization failure that the app must retry — correct but more overhead than option 2 for something this simple.                                                                                   |
| 7   | Isolation levels         | Postgres defaults to READ COMMITTED. Give a concrete two-transaction scenario where that default silently produces a wrong result, and explain which isolation level (or explicit lock) fixes it — and what it costs you.                                    |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | *(not attempted — guidance below, from you reporting this is past your current knowledge)*                                                                                                                                                                                                                                                                                             | Classic **write skew** example (the standard one, from Postgres's own docs): two doctors, Alice and Bob, are both on-call; the constraint is "at least one doctor must always be on call." T1 (Alice going off-call) reads the on-call count = 2, sees ≥2 so it's safe, sets Alice off-call. Concurrently, T2 (Bob going off-call) reads the count = 2 (before T1 commits), also sees it's safe, sets Bob off-call. Both commit — now **zero** doctors are on call, even though each transaction correctly checked the invariant at the moment it read. This happens under READ COMMITTED, and — this is the subtle part — it *also* happens under REPEATABLE READ / snapshot isolation, because each transaction's snapshot genuinely didn't conflict with the other's *writes* (they wrote different rows). It's fixed by **SERIALIZABLE** (Postgres's SSI detects the read-write dependency cycle between the two transactions and aborts one), or by explicit locking (`SELECT ... FOR UPDATE` on both doctor rows, or a summary row representing "on-call count") to force serialization. Cost: SERIALIZABLE adds dependency-tracking overhead and can abort/retry transactions under contention; explicit locking reduces concurrency by making unrelated transactions on those rows wait.              |
| 8   | Isolation levels         | SERIALIZABLE guarantees no anomalies but isn't free. What actually happens at the engine level when it's used (e.g., serialization failures), and how should application code handle that?                                                                   |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | *(not attempted — guidance below)*                                                                                                                                                                                                                                                                                                                                                     | Postgres implements SERIALIZABLE via **SSI (Serializable Snapshot Isolation)** — it doesn't take heavy locks up front; transactions run concurrently under ordinary snapshot isolation, while Postgres tracks read/write dependencies between them (via SIREAD "predicate" locks marking what each transaction *read*). Before allowing a commit, it checks whether the pattern of dependencies among concurrent transactions forms a "dangerous structure" (in practice, a cycle) that could not have arisen from any valid serial ordering. If it finds one, it aborts one of the transactions with a `serialization_failure` error (SQLSTATE `40001`) — this can happen at any point, including at COMMIT. Application handling: catch that specific error and **retry the entire transaction from the start** (not just the last statement), since the data it read may no longer be valid; wrap this in a retry loop with backoff, and make sure the transaction's logic is safe to re-run. Because retries become more frequent under contention, throughput is lower than READ COMMITTED — so SERIALIZABLE is typically applied selectively to the few transactions that truly need the guarantee, not the whole application.                                                                          |
| 9   | Partitioning vs Sharding | What's the actual difference between partitioning and sharding? Where does one stop being enough and force you into the other?                                                                                                                               |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | *(not attempted — guidance below)*                                                                                                                                                                                                                                                                                                                                                     | **Partitioning** splits one logical table into multiple physical segments (by range, list, or hash) **within the same database instance** — same machine, same storage/CPU/memory pool, one engine. It's mostly transparent to the app: the query planner does partition pruning to only touch relevant partitions, and it's great for lifecycle management (e.g. drop old monthly partitions) and keeping indexes/vacuum manageable on a huge table. **Sharding** splits data **across multiple separate database instances/machines**, each typically a fully independent DB with its own storage, CPU, and memory. The application (or a routing layer) must know which shard holds a given row's data. Where partitioning stops being enough: it still only has the resources of *one* machine — total write throughput, RAM, and disk IOPS are capped by that single node, no matter how well the table is partitioned. Once the workload's throughput or storage needs exceed what a single machine can serve — i.e. you've hit the ceiling of vertical scaling even with ideal partitioning — you're forced into sharding to add more machines' worth of resources.                                                                                                                                    |
| 10  | Sharding                 | You're picking a shard key for a multi-tenant app. What makes a shard key good or bad, and what's the specific failure mode when one tenant is 100x bigger than the rest?                                                                                    |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | *(not attempted — guidance below)*                                                                                                                                                                                                                                                                                                                                                     | A good shard key has **high cardinality** (many distinct values, so it can spread data/load evenly), **distributes read/write load roughly evenly** across shards, and **aligns with the dominant query pattern** so most queries resolve to a single shard rather than fanning out to all of them ("scatter-gather"). It should also be stable over an entity's lifetime — changing a shard key means physically moving that entity's data. A bad shard key is low-cardinality (e.g. a boolean), monotonically increasing (e.g. an auto-increment ID or timestamp, which concentrates all new writes on one "hot" shard), or one that doesn't match how data is queried (forcing cross-shard joins/scans). Failure mode for a 100x-bigger tenant, sharded by `tenant_id`: that tenant becomes a **hot shard / noisy-neighbor** — its shard absorbs disproportionate CPU, disk I/O, and storage compared to every other shard, can become a bottleneck (or outright exceed one shard's capacity) while the rest sit underutilized. Mitigation: sub-shard large tenants (e.g. a composite key like `tenant_id + hash(user_id)`), or give oversized tenants their own dedicated shard(s).                                                                                                                       |
| 11  | Sharding                 | Once you shard, how do you generate globally unique IDs, and what happens to joins that used to be a single SQL query across two now-sharded tables?                                                                                                         |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | *(not attempted — guidance below)*                                                                                                                                                                                                                                                                                                                                                     | Per-shard auto-increment IDs collide across shards, so you need a strategy that's globally unique without needing shards to coordinate on every insert: **UUIDs** (random, zero coordination, but not naturally sortable and larger/less index-friendly), **Snowflake-style IDs** (timestamp + shard/worker ID + sequence number packed into one integer — sortable by creation time, compact, only needs a one-time worker-ID assignment, no per-request coordination), or a **centralized ID service/ticket server** (simple to reason about but adds a shared dependency and potential bottleneck). Joins: a join that used to be one SQL query across two tables can no longer be — since the tables now potentially live on different shards, the DB engine has no way to join them in a single query. Options: (1) **application-level join** — query each shard separately and join the results in app code (fine when the join is small/selective); (2) **denormalize** so frequently-joined data is duplicated and co-located within the same shard; (3) **scatter-gather** — query all shards and merge in the app (expensive, avoid on hot paths); (4) maintain a separate **read-optimized store** (search index, analytics DB, or materialized view) that pre-joins data pulled from all shards. |
| 12  | Sharding                 | Your access patterns have drifted since you picked the shard key a year ago. What's the actual process for resharding/rebalancing live data with minimal downtime?                                                                                           |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | *(not attempted — guidance below)*                                                                                                                                                                                                                                                                                                                                                     | Typical low-downtime resharding process: (1) provision the new target shard topology; (2) use **consistent hashing** (or an explicit shard-mapping/directory service) so that changing the shard count only requires moving a small fraction of keys, rather than remapping almost everything the way naive `hash(key) % N` would; (3) for the keys that must move, **dual-write** — start writing to both the old and new shard for those keys, backfill their historical data into the new shard in the background, then verify consistency (row counts/checksums); (4) **cut over reads** for each migrated key range/tenant to the new shard once its backfill+verification is done, via an indirection layer (a shard directory/config service) that clients consult rather than hardcoding shard locations; (5) stop dual-writing to the old shard for migrated keys and clean up the old copies after a safety window. The two techniques doing the real work here are consistent hashing (minimizes data movement) and a routing/indirection layer (lets you update the mapping without touching client code) — tools like Vitess or Citus automate much of this split/move machinery.                                                                                                                |
| 13  | Trade-offs               | A senior engineer says "scale up and add read replicas/caching before you shard." Why is that the right default, and what's the actual signal that tells you a single node/DB is no longer enough?                                                           |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | *(not attempted — guidance below)*                                                                                                                                                                                                                                                                                                                                                     | Sharding adds serious, permanent operational complexity: cross-shard joins/transactions become hard, you need globally unique ID generation, resharding/rebalancing machinery, more infrastructure to run, and application code has to become shard-aware everywhere. Vertical scaling (a bigger machine) plus read replicas and caching are far simpler, fully reversible, and cover the large majority of scaling problems — most production workloads are read-heavy, and modern hardware (multi-terabyte RAM, dozens of cores, fast NVMe) pushes the single-node ceiling much higher than people assume. The actual signal that a single node is no longer enough: **write throughput or data size that saturates the primary even after vertical scaling and adding read replicas** — specifically, all writes still funnel through one primary, so if its CPU/IO/disk is saturated by writes (not reads), replicas can't help at all, and neither can caching, since caching only reduces read load. That write-side ceiling — not "the database feels slow" — is the real forcing function for sharding.                                                                                                                                                                                               |
