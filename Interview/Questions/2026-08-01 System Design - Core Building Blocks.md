| 1   | Load balancing              | You have 5 app servers behind a load balancer, all identical. Compare round-robin vs least-connections vs consistent-hashing as the balancing strategy — for each, describe a traffic pattern where it clearly wins or loses, and what happens to each when one server gets slow (not down, just slow).                                                                                                                    | # > Round robin<br><br>_(evenly rotates requests, no awareness of load)_<br><br>- **Good traffic pattern:**  <br>    When **all requests cost about the same** (e.g., simple API calls, static content).  <br>    → Every server gets equal work, so it’s naturally balanced.<br>- **Bad traffic pattern:**  <br>    When **requests have very different cost** (e.g., some take 5ms, others take 5s).  <br>    → A server that gets a few “heavy” requests becomes overloaded while others are idle.<br>- **If 1 gets slow:**  <br>    Round robin **keeps sending traffic to it anyway**.  <br>    → That slow server builds up a queue → latency increases → can drag down overall system performance.<br><br>---<br><br># > Least connections<br><br>_(send traffic to the server with the fewest active requests)_<br><br>- **Good traffic pattern:**  <br>    When requests are **long-lived or variable in duration** (e.g., WebSockets, streaming, slow DB queries).  <br>    → It adapts dynamically and avoids overloading busy servers.<br>- **Bad traffic pattern:**  <br>    When **“number of connections” ≠ actual load**  <br>    (e.g., one request is CPU-heavy, another is cheap but both count as 1).  <br>    → It may still send traffic to a “light-looking” server that is actually overloaded.<br>- **If 1 gets slow:**  <br>    That server accumulates more active connections →  <br>    the algorithm **naturally avoids sending new traffic to it**.  <br>    → This is a **self-correcting behavior** (better than round robin).<br><br>---<br><br># > Consistent hashing<br><br>_(route based on a key, e.g., user ID → same server)_<br><br>- **Good traffic pattern:**  <br>    When you need **stickiness / locality**, such as:<br>    - caching (same user → same cache)<br>    - sessions<br>    - sharded data  <br>        → Improves cache hits and reduces cross-server coordination.<br>- **Bad traffic pattern:**  <br>    When **key distribution is uneven (hotspots)**  <br>    (e.g., one user/key gets 90% of traffic).  <br>    → That server becomes overloaded while others are underused.<br>- **If 1 gets slow:**  <br>    Requests mapped to that server **keep going to it** (because of hashing).  <br>    → That subset of users suffers high latency.  <br>    → The system does **not automatically rebalance** unless you add extra logic (like replication or fallback).<br> |            |            |
