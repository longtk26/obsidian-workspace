| 2   | Layers / union FS             | Explain what a Docker image layer physically is on disk, why image layers are read-only, and what the "writable container layer" is for. If a running container writes a 2GB temp file and then deletes it in a *later* `docker exec`, does the image itself shrink? Does the container's disk usage shrink?                 | - When building an image it will be saved at /var/lib/docker... with multiple overlay (at linux and readonly status)<br>- The "writable container layer" is used when we run container from an image, with it we can add new file to container or update config in container but doesn't affect to image itself, after editing if we don't commit to create new image, that update/changes will be gone<br>- A running container writes a 2FB temp file the deleted by docker exec will not shrink image size, but the container's disk is shrink | Good — matches how OverlayFS actually behaves. One nuance was missing (see fix).                                                               | A layer is a directory of file diffs stored on disk under `/var/lib/docker/overlay2/<id>` (or another storage driver), identified by a content hash. Layers are read-only so the *same* layer can be shared and reused unmodified across many images/containers without copying it — that's the point of the union filesystem. The writable container layer is a fresh, empty layer stacked on top at `docker run` time; every write goes there via copy-on-write, and it's deleted with the container. Writing then deleting a 2GB file *within that writable layer* nets back to ~0 extra disk there — image size is untouched either way (a running container never touches image layers), and the container's disk usage does shrink back down. If the file had instead existed in a lower read-only layer, "deleting" it from the container only adds a small whiteout marker in the writable layer — the space isn't reclaimed until the image is rebuilt/pruned.                                                                                                                                                                                                                                                                                                                           |
| 3   | RUN cache key mechanics       | You have `RUN apt-get update && apt-get install -y curl`. You rebuild the image weeks later with no Dockerfile changes and Docker reuses the cached layer instantly — even though upstream `curl` has since released a new version. Why does Docker do this, and what's the concrete production risk?                        | I still not know about this                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Correctly flagged as unknown — core cache-invalidation gap, worth memorizing.                                                                  | Docker's RUN cache key is based purely on (1) the parent layer's cache ID and (2) the *literal text* of the RUN instruction — it never executes the command to check whether the result would actually differ. Same instruction string + same parent layer = cache hit, forever, regardless of what changed upstream (new curl release, new CVE patch, etc.). **Production risk:** the image can silently ship a months-old, unpatched, potentially vulnerable package even though the Dockerfile is "unchanged" — builds aren't reproducible over time, and you won't get security patches unless you force invalidation (`docker build --no-cache`, bump a version pin, or use an `ARG CACHEBUST`/date arg to bust the cache deliberately on a schedule).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

| 6   | Multi-stage builds            | Why use a multi-stage build for a compiled Go binary or a bundled React app instead of a single-stage Dockerfile? Walk through how it affects both final image size and cache behavior — specifically, does invalidating the cache in the build stage force a rebuild of the runtime stage's own layers?                     | - When use multi-stage the final stage will decide the size of the image. If run only single file, many redundant resources will be saved in image<br>- About the cache behavior I still not clear here now<br>- About invalidate cache, it doesn't force a rebuild. It get the state previously invalidate cache like update source code or anything related                                                                 | Size/purpose reasoning is solid; the cache-behavior gap you flagged is the interesting part of this question — filled in below.                | Multi-stage builds let a heavy "builder" stage (compilers, dev deps, source) produce artifacts (a compiled binary, bundled JS), then `COPY --from=builder` pulls only those artifacts into a clean, minimal runtime stage — so the final image never contains compilers/source/dev-deps, shrinking size and attack surface.<br>**Cache behavior:** the builder and runtime stages are cached *independently*, each keyed on its own instruction chain and base image — invalidating the builder stage's cache (e.g. source changed) does **not** force the runtime stage's own earlier layers (its `FROM`, `apt install`, etc.) to rebuild. | 7   | Build context / .dockerignore | You forgot a `.dockerignore` and your build context includes `node_modules/` and `.git/`. | 8   | BuildKit cache mounts         | For a Dockerfile that does `RUN npm install`, what's the practical difference between relying on plain layer caching vs. using `RUN --mount=type=cache,target=/root/.npm`? Describe a concrete scenario (hint: CI) where layer caching alone gives you *no* benefit but a cache mount still does.                            | (left blank)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Left blank — BuildKit-specific and easy to miss without hands-on use.                                                                          | Plain layer caching for `RUN npm install` caches the *whole layer* keyed on the parent layer + instruction text. If anything upstream changes (e.g. `package.json` via the preceding `COPY`), the layer is a full cache miss and `npm install` reruns from a completely empty cache, re-downloading every package over the network. A cache mount, `RUN --mount=type=cache,target=/root/.npm`, gives npm a persistent cache directory that BuildKit manages *outside* the image/layer cache entirely — it survives even when the layer itself is invalidated, so npm can reuse previously downloaded tarballs and only fetch what's new.<br>**Concrete CI scenario:** most CI runners start cold — a fresh VM/container with no previous Docker layer cache available at all (or `--no-cache` is used) — so plain layer caching gives *zero* benefit; `npm install` re-downloads everything every run. But if the CI pipeline persists/restores the BuildKit cache-mount directory across runs (e.g. GitHub Actions cache, or a registry-backed cache), the cache mount still speeds up installs on that cold build, because it's decoupled from whether the image layer cache exists at all.                                                                                                     |

Tradeoff: more complex Dockerfile, easy to forget to copy a shared runtime lib/dependency the builder had implicitly.<br>2. **Minimal base images** (`alpine`, distroless, `-slim`) instead of full Debian/Ubuntu. | 10  | CMD vs ENTRYPOINT             | What's the actual difference between CMD and ENTRYPOINT, and what happens when a Dockerfile specifies both? What does `docker run myimage arg1` do differently depending on which one is set, and why would you deliberately use both together?                                                                              | (added directly this session, not yet attempted)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | N/A — added and answered for reference.                                                                                                        | **ENTRYPOINT** sets the fixed executable that always runs when the container starts — it defines what the container *is* (e.g. wraps your app binary or an init script). **CMD** supplies default arguments — either to that ENTRYPOINT, or, if no ENTRYPOINT is set, CMD is the entire command that runs.<br>**When both are specified** (exec form): CMD's value becomes the default *arguments* appended to ENTRYPOINT — e.g. `ENTRYPOINT ["node"]` + `CMD ["server.js"]` runs `node server.js`. Running `docker run myimage worker.js` overrides CMD only, so it runs `node worker.js` — ENTRYPOINT itself is untouched unless you pass `--entrypoint` explicitly.<br>**Shell form is a gotcha:** if ENTRYPOINT is written in shell form (`ENTRYPOINT node server.js`), Docker wraps it in `/bin/sh -c`, and CLI args / CMD are ignored entirely.<br>**Why use both:** ENTRYPOINT locks in "this is what this container does" (often a setup script like `docker-entrypoint.sh` that does init work then `exec`s the real process), while CMD gives callers overridable defaults — e.g. Postgres's ENTRYPOINT handles initialization and always runs `postgres` under the hood, while CMD supplies default flags you can override at `docker run` time without touching the entrypoint logic. |
